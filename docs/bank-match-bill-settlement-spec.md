# Bank-Match → Bill Settlement Spec

**Date:** 2026-09-01 · **Status:** Built for single-bill settlement, both home and foreign currency (see §8/§9) — §2.1 (bill_id tagging), §2.3 (FX allocation reuse, both the bug fix and the actual booking-rate journal entry + settlement), §3 (settle-on-approve), and §3.1 (human-controlled Full/Partial toggle + hard block on missing FX setup) are shipped. Only §2.2 (1:N — multiple bills in one bank line) remains deferred, not built.
**Scope:** Close a gap found by direct code inspection (not inferred from any spec): a bank statement line that `bank.match`'s Tier 2 (open-item matcher) matches against an open bill, and whose resulting `journal_proposals` row is then approved through Inbox, posts a journal entry but never marks the bill paid or partial. `bill.payment.record` (the New Payment page, `/payment/new` — `p`/`P` on `payables-bills.js` before bill-post-payment-consolidation-spec.md, 2026-09-02) is the only path today that actually settles a bill. This spec brings bank-match approval up to parity with that path — matching, not inventing, how QuickBooks Online and Xero already treat bank-feed matching as an authoritative payment-recording action.
**Depends on:** `bank-matching-spec.md` (§4 Tier 2 — this spec amends it), `settlement.js` (`buildAllocationLines` reused as-is; `settleBillPayment`/`settleMultiBillPayment` **refactored**, not called, to extract a shared non-journal-posting `applyBillSettlement` helper — see §3), `p131-multi-bill-settlement-spec.md` (the multi-bill allocation shape §2.2's N:1 case follows), `agent-readiness-spec.md` (R1/R7/R8, single-gateway rule — `bank.match` stays non-mutating; verify this spec's approve-time hook doesn't cross a boundary that spec draws elsewhere — flagged §5 as unverified by this document).
**Companions:** `payables-ux-spec.md` (P1-9, the original single-bill settlement design), `keyboard-ux-spec.md` (no new keybinding — this is a backend behavior change under the existing `y`-approve verb in Inbox).
**Consumers:** `api/src/bank.js` (`matchLine`, Tier 2 branch — bill_id tagging, 1:N restructuring, FX allocation, the `matchOpenItem` home-currency fix), `api/src/journal.js` (`approveProposal` — new `applyBillSettlement` calls), `api/src/settlement.js` (`applyBillSettlement` extracted and reused by both `settleBillPayment`/`settleMultiBillPayment` and the new approve-time hook), `api/src/bills.js` (`voidBillPayment` — reused as-is, not modified).

## 0. The gap, verified end to end

Traced the full path from match to approval, not assumed:

1. `bank.js`'s Tier 2 branch (`matchLine`, ~L300–358) builds a proposal's `lines` as plain `{account_code, debit, credit, date, description}` objects. **No `bill_id` field is set anywhere in these lines** — confirmed by reading the object literals directly, not by absence of a mention.
2. When that proposal is approved (Inbox `y` key → `journal.approve` → `approveProposal`, `journal.js` L1111), it re-validates and calls `postJournalBatch` (L391), which inserts the lines into `journal_entries` — including whatever `bill_id` each line carried (`bill_id: line.bill_id || null`, confirmed at three separate insert sites in `journal.js`: L232, L441, L917). Since Tier 2 never set one, it posts `bill_id: null`.
3. Neither `approveProposal` nor `postJournalBatch` contains any reference to `amount_paid`, `bills SET`, or `bill_payments` — confirmed by grep across `journal.js`, zero hits. The bill's own row is untouched.

Net effect today: the journal entry exists and is correct, but the bill it was for still shows `posted`/`partial` with its full outstanding balance, indefinitely, until someone separately records a manual payment (New Payment) against the same bill — which would then **double-pay it** in the ledger (two settlement journals for one real-world payment) if nobody notices the bank-match already covered it. That double-pay risk, not just the stale status, is the actual severity here.

## 1. Scope

**In scope:** Tier 2 (open-item) matches only — 1:1, 1:N (one bank line, multiple bills), and N:1 (installments, already deterministic per `bank-matching-spec.md` §4.2). These are the cases where `bank.match` already deterministically knows which bill(s) a line settles.

**Out of scope:** Tier 4 (LLM-batched, narrated, N:M) proposals. `bank-matching-spec.md` §4.2 deliberately doesn't pre-identify N:M groups — they fall through to tier 4 as ordinary residual lines, narrated by the LLM. Whether an LLM-narrated proposal should be allowed to carry a `bill_id` and trigger settlement on approval is a materially different trust question (agent-readiness-spec's R7/R8 boundaries around what an LLM's output is allowed to mutate) and is **not decided here** — see §5.

## 2. Design — tagging bill_id at match time (Tier 2)

Three distinct changes to Tier 2, of clearly different size — do not treat them as one edit.

### 2.1 bill_id tagging (small)

For the 1:1 case, Tier 2's existing single AP-account line gains one field: `bill_id: bill.bill_id` (on the AP-side line only, not the bank line — mirrors `settlement.js`'s `mkRow` convention). This is the entire change for 1:1: one field added to an existing object literal, no structural change to how the lines array is built.

### 2.2 1:N lines-array restructuring (larger, distinct change)

The 1:N case (one bank line settling multiple bills — `bank-matching-spec.md` §4.2) is **not** the same change as §2.1 scaled up. Tier 2's `matchLine` today always returns exactly 2 lines (one AP-side, one bank-side) — that shape is hardcoded, not parameterized by bill count. Supporting 1:N requires actually restructuring how the `lines` array is built: one AP-debit line **per matched bill** (each carrying its own `bill_id` and its own share of the total), plus a single shared bank-credit line for the sum — the same N-lines-plus-one-bank-line shape `settleMultiBillPayment` (`settlement.js`) already produces for New Payment's multi-bill mode (`p131-multi-bill-settlement-spec.md` — the `Shift+P` panel that originally shipped it is retired, the settlement code is not), but Tier 2 has no equivalent code today and needs it built, not just extended. Budget this as its own implementation task, not a corollary of §2.1.

### 2.3 FX allocation reuse — and a pre-existing bug it surfaces

Tier 2 today builds a plain 2-line match with no FX-awareness. A bill whose currency differs from home currency needs the same allocation `buildAllocationLines` already provides (`{bill, allocAmount, bankRate, fxAccount, homeCurrency}`) rather than a naive same-currency debit/credit. This spec requires Tier 2 to call `buildAllocationLines` for any matched bill where `bill.currency !== homeCurrency`, reusing the existing booking-rate/FX-gain-loss logic verbatim.

**Pre-existing bug this surfaces, must be fixed as part of this work:** `matchOpenItem` (`bank.js` L124) hardcodes the home-currency comparison — `bill.currency && bill.currency !== 'USD' /* home */`. This is wrong for any company whose home currency isn't USD (e.g. an SEK-home company, which this codebase already supports per its jurisdiction packs) in both directions: a genuine home-currency SEK bill gets misclassified as `fx_rounding` (since `'SEK' !== 'USD'`), while a genuinely foreign USD bill on a USD-home company is never flagged as foreign at all. `matchOpenItem` doesn't currently take a `homeCurrency` parameter — `matchLine` (its caller) will need to fetch `companies.currency` (already queried elsewhere in this file's sibling functions in `bills.js`, just not currently plumbed into `matchLine`) and pass it through, replacing the literal `'USD'`. This isn't optional cleanup — §2.3's FX-allocation work depends on correctly knowing which bills are actually foreign, and the hardcoded value would silently corrupt that determination for any non-USD-home company.

## 3. Design — settling on approve

**This is inline side-effect code added to `approveProposal`, not a call to `settleBillPayment`/`settleMultiBillPayment`.** Those two functions each call `bulkInsert('journal_entries', ...)` themselves — the journal entry for a bank-matched settlement was **already posted** by `postJournalBatch`, from the proposal's own lines (now `bill_id`-tagged per §2). Calling `settleBillPayment` at approve time in addition would **post a second, duplicate journal entry** for the same real-world payment. Do not call either function from `approveProposal`.

**What to actually reuse:** `settleBillPayment`/`settleMultiBillPayment` each contain the exact same three-step tail after their journal-posting step — compute `newAmountPaid`/`newStatus`, `UPDATE bills`, insert a `bill_payments` row (this pattern is duplicated three times already in `settlement.js`: L184–195, L217–228, L421–450). Extract that tail into one shared helper — e.g. `applyBillSettlement({ bill, settledAmount, batchId, method, paymentReference })`, returning `{ paymentId, newStatus, amountPaid }` — that does **only** the bills/bill_payments/event side effects and **never touches `journal_entries`**. Refactor `settleBillPayment`/`settleMultiBillPayment` to call it after they finish posting their own journal (behavior-preserving refactor, no functional change to the manual New Payment paths). `approveProposal` then calls this **same helper directly**, once per distinct `bill_id` on the just-posted batch, with `method: 'bank_match'` (distinct from `'manual'`, so payment history shows which path recorded it) and **no journal-posting call of its own** — the amount comes straight from the line's own debit value, no re-run of `buildAllocationLines` needed at approve time (that ran once, at match time, per §2).

**Idempotency/rollback:** `approveProposal` already wraps `postJournalBatch` in a compensating-rollback block (delete the posted batch, restore `status='proposed'` on failure — `journal.js` L1191–1213). The `applyBillSettlement` calls go inside that same wrapped block, so a failure partway through (e.g. a concurrent void racing the same bill) rolls back the journal batch too, exactly like a `postJournalBatch` failure does today. No new transaction boundary — extending the existing one.

**Void reuse — no new code needed.** `bill.payment.void` (`bills.js` `voidBillPayment`, L818) keys entirely off `bill_payments` rows and calls `journal.reverse` on the batch — it does not care how the `bill_payments` row was created. Writing that row at approve time (§3) means `x` (void payment) on a bank-matched settlement works immediately, for free, through the existing single-bill and multi-bill void paths (`isMulti` branch already exists at L836). This spec adds zero lines to `voidBillPayment`.

### 3.1 Human-controlled Full/Partial toggle, and a hard block on missing FX setup

Two requirements ratified by magnus, refining §3/§4.4's foreign-bill settlement: the system must never *guess* whether a bank-matched foreign payment closes the bill or leaves it open, and must never post a settlement it cannot compute correctly.

**The toggle.** `bank.match`'s foreign-bill path (§2.3/§4.4) stores its default Full/Partial classification (`fx_rounding` → full, `partial_payment` → partial) as `settlement: {billId, mode, blocked}` on the match result, which flows into `journal.propose`'s `_match_meta` and is persisted on `journal_proposals.match_meta`. A human reviewer overrides this via a new `bank.match.toggleSettlement` action (`{proposalId, billId}`) — surfaced in Inbox as a `~`-keyed true/false toggle on the row (no other click buttons control this decision; a keyboard user approves/rejects independently of it). `~` is the app's universal toggle verb (`keyboard-ux-spec.md` §5) and follows the established immediate-persist pattern (`payables-partners.js`'s active-toggle): flipping it writes straight through, no staged/dirty-write step. `toggleSettlement` rebuilds the tagged AP/FX lines for the new mode via `buildFxSettlementLines`, then re-runs `enrichAndValidate` (the same pipeline `journal.propose` uses) over the merged line set before storing — the raw `buildAllocationLines` output alone is missing enrichment fields (`currency`, `fx_rate`, `debit_home`/`credit_home`, etc.) that `postJournalBatch` requires already computed at approve time, and skipping this step was caught by a test asserting a NOT-NULL failure on `journal_entries.currency`. The bank-side line is never touched by a toggle: `bankShare` is algebraically identical to the observed bank amount in both modes, so it's recoverable from whichever lines are currently tagged, regardless of which mode built them. `toggleSettlement` bypasses `journal.propose`'s upsert path deliberately (a direct, scoped `UPDATE journal_proposals ... WHERE status='proposed'`) — that path is actor-restricted to the original proposer, so a human reviewer (a different actor) could not use it.

**The block.** If `buildFxSettlementLines` cannot compute a correct settlement — no valid booking `fx_rate` on the bill, or real FX drift with no FX Gain/Loss account configured — it returns `{blocked: true, blockedReason}` instead of guessing or falling back to an imprecise entry. `journal.approve` checks `match_meta.settlement.blocked` before any state mutation (before the atomic proposed→posted claim) and refuses with a `VALIDATION` error carrying `blockedReason`; Inbox's `y` (approve) verb checks the same flag before even opening the approve modal and surfaces the reason via the banner (`FB.status.show`) instead. A blocked settlement still isn't `bill_id`-tagged (falls back to the pre-existing untagged, human-reviewed path for the underlying journal entry itself), so the entry can still be approved as a plain, unsettled journal batch if the reviewer chooses to fix the bill's FX rate or the account setup and re-match later — the block only prevents settlement being silently skipped or guessed.

## 4. Open question this spec does not resolve — discrepancy types vs. paid/partial

`validateBillForPayment` (`bills.js` L600) throws if the settled amount exceeds outstanding, but silently allows any amount *below* outstanding and marks the bill `partial` — including `bank-matching-spec.md` §4.1's `early_payment_discount` and `bank_fee_netted` discrepancy types, where the vendor's own intent is "this bill is fully settled, the shortfall is an agreed discount/fee," not "there's a remaining balance to collect." Settling those as `partial` is technically consistent with today's manual-payment behavior (a human recording an early-payment discount via New Payment today gets the same `partial` outcome) but will leave a bill permanently dangling at a few percent outstanding with no further payment ever coming. **This spec does not change that behavior** — it inherits whatever `validateBillForPayment`/`recordBillPayment` already do for a same-shaped manual entry — but flags it as a pre-existing rough edge that bank-match approval will now surface far more often (Tier 2 actively looks for these discrepancy types; a human manually paying a bill rarely deliberately underpays). Worth a follow-up decision (write off the discrepancy to an expense account automatically? require human confirmation before treating discount-type matches as final?) but is out of scope for closing the core gap in §0.

## 5. Open question — agent-readiness boundary

`bank-matching-spec.md` states `bank.match` is `mutating: false` and frames matching as strictly separate from the human-approved posting step (single-gateway rule, `agent-readiness-spec.md`). This spec keeps that boundary intact for the *match* itself — Tier 2 still only proposes, same as today, per §2. The new mutation (bill settlement) happens exclusively inside `journal.approve`, which is already a human-gated, `data_entry`-role action, not something `bank.match` or the agent triggers directly. This spec believes that keeps it inside the existing R1/R7/R8 boundary, but that has not been independently verified against the full text of `agent-readiness-spec.md` in this session — worth a check before implementation.

## 6. What does not change

- Tiers 1, 3, and 4 of `bank.match` — untouched.
- `bill.payment.record`'s external behavior (manual New Payment single/multi-bill paths) — unchanged from the caller's perspective; internally, `settleBillPayment`/`settleMultiBillPayment` are refactored per §3 to call the extracted `applyBillSettlement` helper instead of inlining its logic, but produce identical journal entries, bill updates, and `bill_payments` rows to today.
- `voidBillPayment` — untouched (§3 confirms it doesn't need to be).
- The propose/approve boundary — matching still only proposes; only approval mutates.

## 8. Implementation status (2026-09-01) — shipped vs. deferred

**Shipped, single-bill, both currencies:** §2.1 (bill_id tagging), §2.3 (the `matchOpenItem` USD-hardcode fix, and now also the actual FX allocation — `bank.js` calls `buildAllocationLines` to build a proper booking-rate entry for a matched foreign bill instead of a naive 2-line one at the raw bank amount), and §3 (settle-on-approve via `applyBillSettlement`, generalized to sum every line sharing a `bill_id` — not just one — and to branch on currency: foreign bills derive `settledForeign` from the AP line's debit divided by the bill's own booking rate, home-currency bills use the debit directly). Two sub-cases for foreign bills:
- **`fx_rounding` (closing payment):** settles the full remaining foreign balance; the implied actual rate is backed out from the observed bank amount, and the difference from the booking rate posts to a genuine FX gain/loss line when one is configured (or a negligible-diff 2-line entry when the drift rounds to zero).
- **`partial_payment`:** assumes the booking rate applies (no way to separately know rate vs. amount from one bank-side number) — a clean 2-line entry, no FX line, leaving true reconciliation to whichever later payment closes the bill as `fx_rounding`.
- **No FX Gain/Loss account configured, but real drift exists:** falls back to the pre-existing untagged, human-reviewed path rather than either post an unbalanced entry or silently misstate the settlement math — documented in `bank.js`, not separately tested.

Covered by 10 tests total in `api/test/contract.test.js` (3 from the original home-currency pass, 5 from the FX work, 2 from §3.1): the USD-hardcode regression, a zero-drift foreign exact-match-turned-fx_rounding case (now bill_id-tagged, 2-line), a full ref-corroborated fx_rounding case with a real ~5% drift (3-line balanced entry, end-to-end propose→approve→paid with foreign-currency `amount_paid` and correct `bill_payments.amount`/`amount_foreign`), a genuine partial-payment case (2-line, bill stays `partial`), a missing-FX-account block (settlement.blocked, journal.approve refused pre-mutation, bill/proposal untouched), and a full↔partial toggle round-trip (rebuilt lines re-balance, bank-side total invariant, final approve reflects whichever mode was active). Full suite: 185 tests green.

**Deferred, not built:** §2.2 only — multiple bills settled by one bank line (1:N). `bank.js`'s Tier 2 still only ever builds lines against a single bill; `m.bills` (the 1:N combo case) is excluded from bill_id tagging exactly as before, untagged and human-reviewed. The `outstanding`-column currency-mixing bug that originally blocked this work is now moot for the *settlement* side (§2.3's foreign-bill path derives its own currency-consistent numbers independently, per `bank-matching-spec.md` §4.4) but still applies to §2.2's own combination search, which continues to use that same buggy column — a prerequisite for 1:N specifically, not for anything else in this spec.
