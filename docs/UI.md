# UI / UX Philosophy

This document defines the design and accessibility standards for freeBooks UI. All contributors should follow these guidelines.

**Status:** revised 2026-09-06 after an audit found the previous version (2026-05-05) diverged from ~80% of shipped screens on its two central rules (font-size units, colour theming). That version was written once and never checked against the app again. This revision:
- keeps the rules the audit found were actually correct,
- corrects the ones that were wrong for this product (the 16px body-text floor; `title` over `aria-label`),
- adds what was missing and is why redesigned screens would otherwise fail to look like siblings (spacing scale, component inventory, button hierarchy, posted-vs-draft language).

If you find yourself violating a rule below because the tokens/components to do it right don't exist yet, that's a bug in this document — flag it, don't route around it with a hardcoded value.

**Update, 2026-09-11:** Inbox (rebuilt 2026-09-09) and Payables were compared directly, page by page, header pixel by header pixel — the process that surfaced most of this revision's `2026-09-11`-dated entries below (Density, Spacing scale, and the several new Components bullets on identity marks, table borders, row keyboard-focus, date format, sort/filter columns, currency columns, and chrome alignment). The throughline: two screens built independently, months apart, both individually reasonable, rarely agree on the small stuff by default — a shared reference page plus a habit of measuring instead of eyeballing is what catches it, not a bigger rulebook. Bank, Accounting, and the rest of the not-yet-redesigned pages should check themselves against these entries directly rather than reopening the same questions from scratch.

`common.css` and every page file under `api/src/pages/*.js` (plus `api/public/fb-core.js` and `common.js`) were brought into full conformance with this revision on 2026-09-06 — zero `pt`/`px`/`em` font-sizes, zero hardcoded hex colours outside a `:root`/`[data-theme="dark"]` block, verified by repo-wide grep and a syntax check of every touched file. `common.css` is the reference implementation: if a page contradicts it, the page is wrong. Two things this pass deliberately did *not* do: it didn't unify the three status-chip class vocabularies (`st-badge`, `badge-*`, `.chip`) into the single component named in the Components section below — each file's existing classes were pointed at the semantic tokens in place, so a page still needs its markup migrated to adopt the unified `fb-chip` component when that work happens; and it left off-scale `rem` values (e.g. `0.833rem`, `1.083rem`) alone where they weren't `pt`/`px` — normalizing those onto the exact scale above is cosmetic tidying, not a rule violation, and wasn't in scope.

---

## Purpose

freeBooks is used by bookkeepers, owners, and auditors working through volume — ledgers, batches of bills, reconciliations. The UI optimizes for **speed, trust, and auditability**, in that order of frequency but not of importance. It is not optimized for delight. A screen that lets an accountant verify 40 rows without scrolling is doing its job better than one that looks nicer with 12.

## Typography

### Core rule: `rem` for font sizes

All font sizes use `rem` units. Never use `pt` or `px` for font sizes. `em` is acceptable only when a value must scale with its *own* element's font-size (e.g. icon sizing relative to an adjacent label), not as a general substitute for `rem`.

`rem` is relative to the root `<html>` font size, so it respects the user's browser/OS default-font-size preference. (It does **not** uniquely respect browser zoom — `Ctrl +`/`Cmd +` scales `px` and `pt` identically. The real reason to use `rem` is the OS/browser default-size preference, not zoom.)

```css
:root {
  font-size: 100%; /* respects the user's default-size preference */
}
body {
  font-size: 0.8125rem;
  line-height: 1.6;
}
```

### The type scale is dense on purpose

This is ledger software: the primary task on most screens is scanning many rows at once (a journal batch, a reconciliation, an aging report), and fitting more of that batch in one viewport is a correctness aid, not just a density preference — it's easier to spot an anomalous row when more of the set is visible together. The scale below is deliberately smaller than a typical marketing-site or consumer-app minimum, and that is intentional, not a shortfall to fix.

| Role | rem | ~px at 16px root | Notes |
|---|---|---|---|
| Page heading (h1) | `clamp(1.375rem, 1.5vw + 1rem, 1.833rem)` | 22–29px | fluid, see below |
| Section heading (h2) | `clamp(1.25rem, 1.25vw + 0.875rem, 1.667rem)` | 20–27px | fluid, see below |
| Sidebar company name | `1.125rem` | 18px | |
| Emphasis / large numeric total | `1rem` | 16px | e.g. a report grand total — use sparingly, this is the *largest* body-adjacent size, not the default |
| Sidebar nav items | `0.917rem` | ~15px | |
| Top-bar nav links / buttons | `0.875rem` | 14px | |
| **Body text / table cells (default)** | **`0.8125rem`** | **13px** | the working default for grids, forms, lists |
| Sub-labels / captions / secondary table text | `0.75rem` | 12px | |
| Small labels (uppercase), dense micro-text | `0.6875rem` | 11px | |
| Decorative carets | `0.625rem` | 10px | |

Numeric/money cells additionally get `font-variant-numeric: tabular-nums` — apply it once, on a shared utility class, not inline per cell. Misaligned decimal columns are a legibility defect in this domain: scanning a column of totals for an outlier depends on digits lining up. Money is right-aligned, fixed decimal places, never wraps.

**Shipped 2026-09-06** as `.amt, .num, th.num, td.num` (common.css) — `.amt` and `.num` were already the two names in use across pages for a numeric cell, both now defined once instead of per-page or not at all. The "not at all" case was real: `journal-voucher.js` used `class="num"` on its Debit/Credit/VAT columns (both header and cell, 8 sites) and `.num` had no CSS rule anywhere in the codebase — those columns had been rendering left-aligned with non-tabular digits since the file shipped, undetected because nothing else about the page looked broken. New numeric/money display uses `class="amt"` (or `"num"` in a `<table>` context, matching the existing header convention) — never inline `text-align:right;font-variant-numeric:tabular-nums` on a per-cell basis, which is exactly how the shared rule went missing from one file's notice in the first place.

### Fluid headings: `clamp()`

Headings use `clamp()` so they scale smoothly without a media query and never get comically large on an ultra-wide monitor. This only applies to `h1`/`h2` — it is not a general pattern for body or table text, which stays at the fixed sizes above.

```css
/* clamp(minimum, fluid-middle, maximum) */
/* min/max must be rem (WCAG 1.4.4: supports 200% zoom); vw belongs only in the middle term */
h1 { font-size: clamp(1.375rem, 1.5vw + 1rem, 1.833rem); }
h2 { font-size: clamp(1.25rem,  1.25vw + 0.875rem, 1.667rem); }
```

### Font family

`'Helvetica Neue', Arial, sans-serif` everywhere. This is the only approved stack — don't declare a page-local font-family or `!important` override it; if a page currently does, that's a cleanup target, not a precedent to extend.

### Rules
1. **`rem` (or `em` for self-relative cases) for font sizes.** No `pt`, no fixed `px`.
2. **`rem` for clamp bounds.** The `vw` component belongs only in the fluid middle expression.
3. **Max ≤ 2.5× min** on any fluid/clamped size (WCAG 1.4.4).
4. **Tabular numerals on all monetary/numeric columns**, applied via a shared class, not inline.
5. **Negative numbers, decimals, and currency placement** follow one convention across the interactive UI, and that convention is **jurisdiction-aware**. **Shipped 2026-09-06** as `FB.util.fmtAmt(n)` (`fb-core.js`), which reads `window.__fbFlags.jurisdiction` (bootstrapped server-side per page via `getRelevanceFlags`/`flagsBootstrapJson`) and picks `sv-SE` for jurisdiction `SE`, `en-SG` otherwise — always 2 decimals. This deliberately tracks the **company's own jurisdiction**, a stable business property of the books being kept, not the viewer's own browser/OS locale: several call sites had previously used `toLocaleString(undefined, ...)`, meaning the *same amount* could render with a period or a comma as the decimal separator depending on whose machine was looking at it, regardless of which company's books were open — a real correctness risk for financial software, not just a style inconsistency.

   This went through two revisions to get right. The first version used a fixed `en-US`-style format with parentheses for negative, copying `reports/render.js`'s internal P&L/BS/TB/GL convention — parentheses is a distinctly Anglo-American accounting convention that reads as foreign in several of the locales this app serves, so that changed to a plain minus sign. The second revision went further: a fixed locale (even with a minus sign) still meant a Swedish company's bills/payments/journal entries used comma-thousands/period-decimal while its own statutory annual report (`report-composite.js`, filed with Bolagsverket) used space-thousands/comma-decimal for the exact same numbers — two contradicting conventions in the same app for the same company's books. `fmtAmt` now mirrors `report-composite.js`'s jurisdiction mapping exactly, so a company's interactive UI and its filed statutory report agree. Note `sv-SE`'s minus sign is Unicode U+2212, not the ASCII hyphen `en-SG`/`en-US` use — by design, from `Intl.NumberFormat` itself; never detect negativity by inspecting a formatted string's first character, check the underlying number.

   Currency itself was already consistent and didn't need a convention change: always the 3-letter ISO code, never a symbol, shown in its own table column or as a text suffix in prose — never prefixed.

   `fmtAmt` is for **display only**. Never use it to set an `<input type="number">`'s `value` — browsers reject or mangle comma- and parenthesis-formatted numbers there; those stay plain `n.toFixed(2)`, exactly as before. And never re-parse a value your own `fmtAmt`-formatted text back out of the DOM (`Number(el.textContent.replace(/,/g,''))` or similar) — `bank-reconciliation.js` did exactly this for its running opening balance, which silently produced `NaN` the moment a negative balance's parenthesized text hit that regex. The fix was tracking the number in a real variable alongside the display, not parsing display text back into data.

   Any page that calls `fmtAmt` must expose `window.__fbFlags` with a `jurisdiction` field before its script runs (see `journal-voucher.js`, `bill-edit.js`, `payment-new.js`, `bank.js`, `inbox.js`, `payables.js` for the pattern) — a page missing this silently falls back to `en-SG` formatting, which is a plausible bug source if a new page is added later without wiring it up.

## Density

Two modes, not a spectrum:

- **Compact (default).** Table rows and table-embedded inputs use the smaller end of the spacing scale below. This is what ships by default everywhere — accounting users want more rows on screen, not more air around them.
- **Comfortable (optional).** Uses the larger end of the spacing scale.

Don't introduce a third density or per-screen bespoke spacing — every screen picks one of these two.

**Shipped 2026-09-06** as a global, user-level toggle (not per-screen) — a topbar button (`fbToggleDensity()`, `common.js`) matching the existing theme toggle's exact mechanism: a `data-density="comfortable"` attribute on `<html>` (absent = compact), persisted per-browser via `localStorage` (not per-company — it's a reading preference, not company data, same reasoning as the theme toggle). The CSS lives once in `common.css` rather than duplicated across the eight files that define the dense edit-grid archetype (`.edit-table`/`.jrnl-table`/`.jv-table`), overriding all eight by selector specificity.

Scope: originally only the dense edit-grid archetype (table cells + their embedded inputs) responded to this toggle. Standalone form fields stay excluded — they already sit at the scale's single "8px 12px" value with no cramped variant to relax from. The `.data-table` browse-list archetype's exclusion, on the other hand, is **superseded as of 2026-09-11** — it was excluded on the theory that it was "already roomy," but that roominess turned out to have no real justification once checked against a sibling page (see Spacing scale below): `.data-table` now defaults to the SAME dense row height as the edit-grid archetype, with Comfortable as its own escape hatch, not a permanently roomier resting state. Migrated: Payables (Bills). Not yet migrated: Bank and any other `.data-table` page — until a page gets its own redesign pass, don't copy its current roomy padding into a new one.

If a table-embedded input ever doesn't respond to this toggle, look for an ID selector styling it directly (an ID always outranks the `[data-density="comfortable"]` override's specificity, no matter how many classes that override stacks) — `calendar.js`'s `#reminder-add-row input` was exactly this, and turned out to be fully redundant with the shared `table.edit-table input[type=text]`/`[type=date]` rule already in the same file, so the fix was deleting the ID rule, not adding a bigger override.

## Spacing & Layout

Use `px` (or unitless/relative values where CSS requires it) for padding, margin, border-width, and gap — not `rem`. Spacing shouldn't track the user's font-size preference the way text does.

### Spacing scale

```
4px · 6px · 8px · 12px · 16px · 24px
```

Pick from this scale; don't introduce arbitrary values.

**Enforced as of 2026-09-06** — the app previously had two verbatim-duplicated table stylesheets (`.edit-table`/`.jrnl-table`/`.jv-table` across 8 files; `.data-table` across 2) whose `td` padding had drifted into 4 different values despite `th` staying identical everywhere. Normalized onto two intentional, named archetypes:

| Element | Dense (edit grids — `.edit-table`, `.jrnl-table`, `.jv-table`) | Roomy (browse lists — `.data-table`) |
|---|---|---|
| Table cell padding (td and th) | `4px 6px` (th: `6px 6px`) | `12px 12px` |
| Table-embedded input padding | `4px 6px` | — |
| Standalone form field / toolbar input padding | `8px 12px` | |
| Section/card padding | `12px` (compact) – `24px` (comfortable) | |

**Corrected 2026-09-11: the "Roomy" column above is legacy, not a target to design new pages against.** It was justified at the time as "browse lists carry avatars, badges, and hover row-actions that need the extra room" — checked directly against Inbox (a dense table with badges and hover row-actions of its own, doing fine at `4px 6px`), that turned out not to hold: the actual thing forcing a roomier row on Payables' Bills table was a 32px partner-avatar identity mark, not browsing itself. Shrinking the avatar to 24px (see Components → Identity marks) let the row converge to the exact same `4px 6px` / `6px 6px` dense values as every other archetype, with **zero remaining functional difference** between "dense" and "roomy" — they're the same numbers now. Treat the table above as: **one archetype, `4px 6px` (th `6px 6px`), always** — pages not yet redesigned (Bank) still carry the old `12px 12px` until their own pass; don't copy it into a new page, and don't reach for it as an option when a screen "feels like it needs more room" — size the content to fit the row instead (Identity marks bullet, Components).

Table row min-height is deliberately **not** set explicitly — rows currently derive their height from padding + line-height + font-size, which already renders consistently once every archetype shares the same padding, and inventing an explicit min-height without a concrete problem to fix risks making rows *less* consistent, not more. Revisit only if a real height mismatch turns up.

### Structural constants

- Top bar height: fixed `52px` — intentional chrome, not part of the density scale.
- Page content max-width: `1100px`. Reference the shared constant/class — don't re-declare the literal per-page.

### Layering

**Verified against real usage 2026-09-06** — the scale originally proposed here (round numbers: dropdown 100, modal 1000, etc.) was never checked against the actual codebase and didn't match it. The real scheme, it turns out, is already coherent and mostly deliberate; the fix here is to this document, not to the code. (The topbar-icon-dropdown stacking bug referenced in the previous version was an Escape-key/multiple-dropdowns-open state bug, not a z-index ordering problem — already fixed separately, unrelated to the numbers below.)

```
sticky table header (.data-table thead)                          : 10
topbar chrome (#top-bar)                                         : 90
topbar popover (company switcher, period picker)                 : 300
topbar dropdown (notifications, download, + New menu)             : 1000
keyboard-shortcut overlay (#fb-keys-overlay, the `?` help panel)  : 9500
modal / dialog (FB.modal)                                         : 9800
dropdown / autocomplete / command palette / column filter          : 9999
  (.fb-dd, .fb-palette, .fb-grammar-hint, .fb-col-filter-dd)
```

The last tier being *highest*, above modals, is intentional and documented in common.css where `.fb-modal-overlay` is defined: dropdowns need to render correctly even when nested inside a modal (an autocomplete field inside a modal form, say), so they stay on top of everything, modals included, rather than getting clipped beneath the modal that hosts them. Don't "fix" this into a more conventional-looking modal-on-top ordering — that would break dropdowns-inside-modals.

New chrome should slot into one of these seven tiers by role, not invent an eighth. If something doesn't fit the categories above, that's worth a real conversation about why, not a guessed number.

## Colour & Theming

All colours use CSS custom properties (`var(--name)`). **Never hardcode a colour value outside a `:root` / `[data-theme="dark"]` block.** This is the most important rule in this document — light and dark themes are both defined and dark mode is a shipped, user-facing feature (topbar toggle, persisted), not a nice-to-have. Any new UI element must work correctly in both.

This rule only works if the token set actually covers what you need. It didn't — that's why ~600 raw hex values exist in the codebase today, standing in for colours (status/danger/success/warning/info, table stripe, input borders, focus rings) that had no token. Adding a new semantic token is the correct fix when you hit this gap; hardcoding a hex value is not.

### Token set

**Shipped in `common.css`** as of the 2026-09-06 remediation pass:

- Existing chrome tokens (`--bg`, `--surface`, `--border`, `--text`, `--text-muted`, `--text-faint`, `--sb-*`, `--tb-*`, `--navy-*`, `--accent`, `--dd-active`, `--toggle-on*`) stay as before, with `--text-muted` corrected in the light theme (`#6b7a95` → `#5f6e89`, fixing a 4.34:1 AA failure — now ≥5:1). `--text-faint` was left failing AA on purpose; see Usage notes.
- `--on-accent` (`#ffffff` in both themes) — text/icons on an `--accent`-filled surface (buttons, the keyboard-focus cursor row). Not in the original proposal; needed once the `#fff`-on-dark-fill literals scattered through `common.css` were being replaced.
- `--focus-ring` (`#2563eb` light / `#93c5fd` dark) — see Accessibility.
- Semantic status tokens, each with a `-bg` and `-border` pair: `--danger`, `--success`, `--warning`, `--info`, and a neutral `--chip-text`/`--chip-bg`/`--chip-border` trio for non-status tags. Values were chosen interactively (contrast-checked against `--surface` in both themes) and seeded from hex values already in use across `api/src/pages` rather than invented from scratch — see the status-chip vocabulary in Components below for how they map to the app's actual status labels.

**Proposed but not needed in practice:** `--row-stripe`, `--row-hover`, `--input-bg`, `--input-border`, `--input-border-focus` were expected to be necessary but weren't — the existing `--bg`, `--border`, and `--surface` tokens already covered every row-hover and form-input case encountered while remediating `common.css`. Introduce a dedicated token only if a real case turns up that these three can't express; don't add them speculatively.

### Usage notes
- `--text-faint` is for **decorative-only** elements (carets, dividers) that don't need to pass text contrast — never use it for text a user is expected to read. If a caption or label needs to be muted but legible, use `--text-muted`.
- Don't invent a one-off hex value because "it's close enough to an existing token" — extend the token set instead, so both themes stay in sync automatically.

## Components

freeBooks already has a de-facto shared component layer (`fb-core.js`, `fb-list.js`, `fb-form.js`). This section names the conventions that layer should converge on; it documents intent, not a finished inventory — expect to extend it as screens are redesigned, but extend it here, not per-page.

- **Table.** Right-aligned numeric columns (tabular numerals, per Typography), sortable/filterable headers, sticky header on scroll, row density per the Density section, zebra via `--row-stripe`, batch actions in a visible bar above the table — not hidden in an overflow menu, inline row actions on hover/focus. An icon-only actions/verb column still gets a header label (e.g. "Actions") — an unlabelled header reads as decoration, not a control. **Shipped 2026-09-09** (Inbox's Transactions/Partners/New Rule/Failed Input tabs) — FB.list's `sortable: true` per-column flag already existed (Bills was the only prior user) but was otherwise undiscovered/unused elsewhere; reach for it before hand-rolling a sort. **No wrapping bordered "card."** A table sits flush on the page — row separation is `border-bottom` on `td`/`th` only, no outer `border`/`border-radius` container around the table itself. **Corrected 2026-09-11**: Payables' Bills table was wrapped in a `.table-card` div (`1px solid var(--border)` + `8px` radius) Inbox's tables never had; the per-cell border-bottom rules were already byte-identical between the two, so this outer frame was the *entire* visible "the grid looks different" difference once actually compared side by side. Removed — `.table-card` is now an unstyled grouping div, kept only because `.pagination-row`'s own `border-top` still wants a sibling container to sit in, not because the wrapper itself should paint anything.
- **Every column backed by real per-row data gets both `sortable: true` and an explicit `filterType`** ('text'/'date'/'amount'/'list', per the field's shape) — this is the default a column should have, not something it opts into one at a time. **Audited & fixed 2026-09-11** across Payables (Bills, Vendors) and Inbox (Transactions, Partners, New Rule, Failed Input): several columns had drifted to filter-only or sort-only (Payables' Reference had filter but no sort, Partner had sort but no filter; Inbox's Description had filter but no sort on all three tabs that carry it) with no comment anywhere explaining why — plain gaps, not decisions. Three genuine exceptions, all narrow: (1) the framework's own trailing row-actions column (chips/verbs) isn't backed by a data field — nothing to sort or filter; (2) a `type: 'checkbox'` column gets `filterType: 'list'` explicitly, never plain `'text'` — `fb-list.js` itself defaults a checkbox column's filter to `null` ("a text box against a checkbox would be noise"), so a working filter there has to be requested with the right type, not left to the framework default; (3) a column backed by a **synthetic** field with no real value on the row (name prefixed `_`, e.g. Inbox's `_doc` source-document badge or Partners' `_source`) must set `filterType: null` explicitly to opt out — `fb-list.js` defaults *every other* column's filter to `'text'` at `FB.list.create()` time whether the page declared one or not, so a synthetic column silently gets a filter button that searches a field that doesn't exist: a dead control, not a missing one, and worse than either extreme. Get the exception wrong in either direction — a real column left unsortable, or a synthetic column left un-opted-out — and it reads as an unexplained small bug, because there's no visible reason left for the gap once you know the rule.
- **A conditional column is shown only when at least one row actually needs it** — a company-level toggle baked in at page load (journal-voucher.js's `FX_ON`-gated CCY field is the precedent) for a column irrelevant to the whole company, or a *currently-visible-rows* toggle for one irrelevant only some of the time. FB.list's columns are fixed for the lifetime of one `FB.list.create()` instance (no API to reconfigure `cfg.columns` after creation — headers are matched to columns by DOM position, wired once), so the latter has to happen at the content/class level. **The standard for a currency column specifically: a dedicated, sortable/filterable column headed "CCY"** (never the spelled-out "Currency") **that collapses when every currently-visible row shares one currency**, not an inline suffix folded into the Amount cell's own text. **Revised 2026-09-11** — this bullet previously held up Inbox's Transactions Amount column (`fmtAmt(amount) + (currency ? ' '+currency : '')`) as the model; that was itself a workaround for not having a real column, and it meant currency could never be sorted or filtered on its own. Payables' Bills table had already solved this properly — promoted to Inbox's Transactions tab too. Mechanism depends on table layout: a `table-layout:fixed` table with a `<colgroup>` collapses the column via `visibility:collapse` on its `<col>` (never `display:none` on the `th`/`td` alone — that slides every later column's cells into the wrong track); a table without a colgroup (auto layout, e.g. `.jrnl-table`) can use plain `display:none` on the `th`/`td` pair keyed by `data-field`, since there's no column-track mapping to break. Either way, never hide the column while a filter *on that column specifically* is active — checking the column's own `.fb-col-filtered` state, not "any filter is active" on the whole list — a list can carry an unrelated permanent default filter (Inbox's Transactions defaults to `status:proposed`) that would otherwise defeat the collapse forever.
- **Table row keyboard-focus (`nav-row-focus`, `fb-list.js`'s default `focusClass`) is a translucent tint, not a solid fill.** `common.css`: `rgba(61, 100, 148, 0.18)` light theme / `rgba(61, 100, 148, 0.35)` dark theme, on the row's `<td>`s — no forced text/link/badge recoloring, normal cell content stays legible straight through it. **Changed 2026-09-11.** The prior default was a solid `var(--accent)` fill (near-black navy in light mode) with `color: var(--on-accent)` forced onto the row's text/links/inputs — every FB.list table used it *except* Payables' Bills/Vendors, which had independently reinvented this exact translucent tint years earlier as a page-local `.bill-row-focus` class. Promoted Payables' version to the shared `nav-row-focus` default and deleted the page-local duplicate; the forced-color overrides are gone too, since a light tint doesn't need them to stay legible. **`.fb-form-cursor` (the FB.form cell-level cursor — bill-edit.js, journal-voucher.js, new-company.js, and any other K3 form page) now converges on the same `rgba(61,100,148,…)` tint, converted 2026-09-11.** It keeps one deliberate difference from the row tint: an `outline: 2px solid var(--accent)` ring on top of the tint, not tint-alone — a single cell has to stay unmistakable during fast keyboard nav in a way a whole highlighted row doesn't (button cells, `.fb-form-cursor-btn`, already used a ring-only treatment for the same reason, pre-dating this change). Dropped the old rule's `color: var(--on-accent)` forcing and its separate `input/select/textarea` descendant-selector block — CELL_CLS lands directly on the control element itself in every zone's `cells()` (never a wrapper), so that descendant rule never matched anything, and normal text/placeholder colors read fine on a tint this light without forcing. That forcing had a real bug hiding behind it: `color` on the input doesn't reach its own `::placeholder`, so an empty focused field's placeholder text (new-company.js's Company ID field, e.g.) rendered dim-gray on navy — near-illegible — until this fix, which needed no placeholder-specific rule at all to resolve it. **`fb-form-row-focus` (the FB.form ROW-level focus, distinct from the cell-level cursor above — journal-voucher.js's `.fb-attach-row.fb-form-row-focus`, its attachment-queue row) converged the same way, same day.** Same prior shape as the row-tint fix: solid `var(--accent)` fill forcing three separate child overrides (`.fb-att-meta`, `.fb-att-del`, `.fb-att-add-btn` all pinned to on-accent/white) just to stay legible on top of it. Now the plain tint, and all three overrides deleted rather than recoloured — `.fb-att-meta`'s text-muted, `.fb-att-del`'s danger red, and `.fb-att-add-btn`'s text-muted (its shared common.css recipe) all read fine on a tint this light with no forcing at all. `tr.fb-form-row-focus > td, div.fb-form-row-focus { background: var(--bg) }` in `common.css` is a separate, already-neutral base rule (used where no page overrides it) — not part of this convergence, nothing wrong with it.
- **Identity marks (avatars, company/user-initial badges) are rounded squares (`border-radius: 5px`), never circles** — matching the topbar's own identity mark (`.tb-mark`, the company-initial badge) and its icon buttons (`.tb-icon-btn`): one shape language for "this represents an identity or a control," not two competing ones. **Corrected 2026-09-11**: Payables' partner avatar (`.avatar`, `payables.js`) was `border-radius: 50%`, a circle introduced with no cross-reference to the topbar convention anywhere in the app. **Size an identity mark to fit the row it sits in, never the other way around.** That same avatar's 32px diameter (+ 8px cell padding) was, on its own, the single thing forcing Payables' Bills rows ~20% taller than every sibling table — even after cell padding itself already matched the dense standard exactly. Shrunk to 24px once nothing else in the row needed the extra height, and row height converged to the shared dense value as a direct result, with initials still perfectly legible at the smaller size. A decorative element that needs more room than the row's own text/badge content already provides is a sign the element is wrong, not that the row needs to grow to fit it.
- **List/table Date columns use the short form: `FB.util.fmtDateShort` (`fb-core.js`)** — year-elided when the date falls in the current calendar year ("21 Jul"), full "21 Jul 2025" otherwise, with the full ISO date carried in the cell's `title` tooltip, never spelled out in the visible text. A one-off detail view (a confirmation-modal "Date: …" line — precision over density, not a scannable list) uses the full form, `FB.util.fmtDate`, instead. **Promoted to `fb-core.js` 2026-09-11**: `fmtDate` already existed there, explicitly commented "the Payables standard" — but was unused; Payables had quietly reinvented an identical local copy instead of calling it, and Inbox had reinvented a *third*, plainer raw-ISO formatter (`String(v).slice(0,10)`, no month name, no tooltip) for the same job. `fmtDateShort` didn't exist shared at all; added alongside `fmtDate`. Both pages now call the shared functions — a new Date column reaches for `FB.util.fmtDateShort`, never a local reimplementation, however small.
- **A list's default (unsorted) row order is exactly one server-side `ORDER BY` applied to the full result set — never two differently-ordered queries concatenated and presented as if they were one list.** If a screen unifies rows pulled from more than one source query (Inbox's Transactions tab merges `journal_proposals` and `bill_draft` rows from two separate tables), sort the COMBINED array by the shared ordering field after fetching both; don't rely on each query's own `ORDER BY` plus a plain concat — two individually-sorted arrays are not, once concatenated, a sorted array. **Found & fixed 2026-09-11**: `journal_proposals` sorted `date DESC` (business date — matching `bill.list`'s own convention), but `bill_draft` rows were appended after as a block sorted `created_at DESC`, a different field entirely; a bill dated last month could sit below a proposal dated a year ago in the untouched default view, because the two blocks were never actually merged, just stacked. `_mergeByDateDesc()` (`api/src/inbox.js`) now re-sorts the combined array by `date` (tiebreak `proposed_at`) before returning it.
- **Structural chrome (page header, tab strip, tab underline, a table's first column header) starts at the identical x/y pixel position on every page** — verify by measuring (`getBoundingClientRect()`), not by eye; a 1–2px gap is invisible in isolation but reads as wrong the moment two pages are open side by side. **Fixed twice in the same session, 2026-09-11** (Payables vs. Inbox): first, a dead `<div class="tb-controls-row">` — a retired toolbar whose markup was never deleted — left a stray 16px margin between the tab strip and the table; separately, `.header { align-items: center }` let a supplementary element (a Bills-only stat strip) that was very slightly taller than the `<h1>` become the flex row's height-determining child, nudging the `<h1>` itself down a fraction of a pixel — invisible alone, but it then cascaded into a much larger, visible gap once that supplementary element grew further. **The fix that holds regardless of viewport width or the supplementary content's own size: take anything that isn't the page's `<h1>` out of `.header`'s height calculation entirely** — `position: absolute` inside a `position: relative` `.header`, vertically centered against it (`top: 50%; transform: translateY(-50%)`), never an in-flow flex sibling sized by its own content. `.header`'s height should be traceable to exactly one thing, the `<h1>`, on every page, no exceptions.
- **A boolean/checkbox column centers under its header**, not left-aligned. The header text already names what's being flagged ("Vendor", "Customer"); a left-aligned checkbox reads as competing with neighbouring text columns for a reading order it doesn't have.
- **A multi-account journal-entry line list collapses debit/credit into ONE signed amount column: debit is positive, credit is negative — mechanically, regardless of account type.** This is not the same as the "signed relative to normal balance" convention a single account's own ledger/statement view uses (there, positive means "moved in that account's normal direction," which requires knowing the account type and would need the opposite sign for a liability/revenue account vs. an asset/expense one). The mechanical DR+/CR− convention is what SAP's own FI documents reduce to when their unsigned amount + S/H debit-credit indicator gets rendered as one signed number — it's correct precisely because a single journal entry mixes account types (an expense DR against a payable CR in the same list) and only the mechanical rule stays consistent across all of them. **Shipped 2026-09-10** (Inbox's Transactions unfold) — replaced two separate Debit/Credit cells (matching the finalized mockup) with one signed cell, a deliberate mockup deviation after this exact question came up.
- **Prefer the informative business fact over an internal reference number as a table's primary at-a-glance column** — e.g. counterparty over a doc/invoice number, when a row could show either. The reference, when present, still belongs somewhere (a `title` tooltip on the cell), just not the primary column. **Shipped 2026-09-09** (Inbox's Transactions tab: Counterparty replaced Doc No, which was empty for every journal-entry row pre-post and, even for a bill, less useful at a glance than who the money's with).
- **A control never implies capability the backend doesn't have.** An interactive-looking element (a dropdown offering choices, a button suggesting an action) that silently does nothing different no matter which option is picked is worse than showing the same information as a plain read-only badge — it teaches the reviewer a false model of what the app can do. **Shipped 2026-09-09** (Inbox's Partners tab Duplicate column): the finalized mockup specified a "create as alias of X" dropdown, but no alias/duplicate-merge concept existed anywhere in the backend (`findFuzzyMatch` only ever returns one best-guess candidate, and there was no merge action at all) — built as the existing informational warning badge instead of a control that would look actionable without being able to actually act. **Follow-up, same day**: `partner.proposal.alias` was then added (resolves a proposal as the same partner as an existing one — no new partner created, source bill relinked, mapping auto-learned from the existing partner's own account) — the Duplicate column is now a real "alias to X" link when the fuzzy hit is against an existing partner (`kind:'partner'`), and stays the plain informational badge only for a hit against another pending proposal (`kind:'proposal'`), which still has no partner_id to alias to. The principle held even though the specific control it was invoked for later became legitimately actionable — it was correct to ship the honest badge first rather than the fake-actionable dropdown while the backend gap was real.
- **Don't restate a count the UI already shows elsewhere as its own text row.** A tab strip with live per-tab counts already answers "how many rows need attention" — a `"N proposed transactions awaiting review"` sentence under the active tab repeats that number in a second place instead of adding information. **Shipped 2026-09-09** (Inbox): each of the 4 tabs had its own `onLoaded` callback writing this kind of sentence into a shared `#queue-note` element; removed once the tab-count badges (added in this same rebuild) made it redundant.
- **A persistent status indicator should be silent when everything is fine, and speak only when something needs attention.** A page that greets every visit with `"Checking status…"` then a permanently-present `"Agent: Running · Feed watcher: Running"` line trains the reader to stop reading it — the same information, shown only when it's *not* the expected/healthy state (as a `hidden`-by-default warning pill), stays meaningful because it's rare. **Shipped 2026-09-09** (Inbox's agent/feed-watcher status: was an always-visible text line in the page header; now `#agent-warn`, `hidden` unless the agent or feed watcher is actually stopped).
- **A `hidden`-toggled element's own CSS class must not set `display` without also pairing it with a `[hidden]` override.** The native `hidden` attribute and a same-file class selector (`.foo { display: ... }`) are equal specificity — as the later-loaded author stylesheet, the class rule wins the tie and silently defeats `hidden` on every element that has both, regardless of whether the attribute is toggled on or off, with no error anywhere. Any element styled as `display: flex/inline-flex/grid/block` etc. that also gets shown/hidden via the bare `hidden` attribute (not a `.classList`-toggled visibility class) needs a paired `.foo[hidden] { display: none; }` rule. **Found & fixed 2026-09-09** (Inbox's `#agent-warn` pill): shipped with exactly this bug — `.agent-warn { display: inline-flex }` with no `[hidden]` override meant the pill rendered unconditionally regardless of the `hidden` attribute JS was correctly toggling; caught only by a user reporting a visible-but-textless pill in production, since every automated check exercised the JS logic, not the resulting computed CSS.
- **A custom control inside an `FB.list` tbody must not use `data-act`.** `fb-list.js`'s `wireChips()` wires a click handler on *every* `[data-act]` element inside its tbody, not just the verb/write/revert/exit values it recognizes — an unrecognized `data-act` value still gets `stopPropagation()`'d and then silently does nothing, since none of `wireChips`'s `if`/`else if` branches match it. A page-local control rendered inside an FB.list cell (a link, a button) needs its own distinctly-named attribute (`data-partner-alias`, not `data-act="partner-alias"`) for a page-level delegated click handler to ever see the click. **Found & fixed 2026-09-09** (Inbox's Partners tab "alias to X" link): shipped with exactly this collision — the click did nothing, with no error anywhere, until caught by live Playwright verification (a syntax check or a render-only check can't catch this class of bug, since nothing throws).
- **Tabs, one `FB.list` instance per tab.** `.tabs`/`.tab`/`.tab.active`/`.tab-panel`/`.tab-panel.active` — **promoted to common.css 2026-09-09** (previously copy-pasted verbatim across accounting.js/settings.js/bank.js/calendar.js/payables.js/inbox.js; reports-hub.js's `.tabs` stays page-local since its full-height flex layout is genuinely different, not a duplicate). A page needing a different look overrides the specific property on top, in its own `<style>` block, after `commonStyle()` in the cascade — see inbox.js's `.tabs { margin-bottom:20px; }`. FB.list's columns are fixed per instance (see the conditional-column bullet above), so a tab strip whose tabs show genuinely different columns needs one `FB.list.create()` per tab, not one instance with a swapped column config — there is no such swap API. Each instance's `active()` callback checks its own `.tab-panel.active` class so only the visible tab's keybindings are live; call `list.renderHints(hintEl)` (not the global `FB.keys.renderHints(...)` directly) on tab switch — it already knows its own `keysId`. Load every tab's list eagerly at page load only if the tab strip itself needs to show live per-tab counts (Inbox); otherwise lazy-load on first visit and cache (accounting.js/settings.js's `tabLoaded[t]` guard).
- **Filter / toolbar bar.** Sits above the table it filters. Filters are visible, not collapsed behind a single "Filters" button, unless the filter count genuinely doesn't fit.
- **Status chip.** One vocabulary, shipped: `.badge` (base shape, `common.css`) plus five semantic modifiers — `.badge-danger`, `.badge-success`, `.badge-warning`, `.badge-info`, `.badge-neutral`. This replaced five independent per-page conventions on 2026-09-06 (`st-badge`/`st-*` in journal-voucher.js and inbox.js, `.badge-out`/`.badge-in`/`.badge-manual`/`.badge-bank_match`/`.badge-voided`/`.badge-posted` in bank.js/bank-payments.js, and three separately-defined bare `.badge` classes with mismatched geometry in bank.js/payables.js/bill-edit.js — two of which, in `payables-bills.js` and `payables-partners.js`, had no definition backing them at all and were rendering completely unstyled). What each page's own status values *mean* (which of the five buckets "voided" or "overdue" maps to) stays local to that page; only the rendering classes are now shared. New status badges use `class="badge badge-<semantic>"` — never a sixth vocabulary, and never an inline `style="background:...;color:..."` on a badge, which is exactly the pattern that left two pages unstyled last time.
- **Action-icon chip vs. filter/tag chip — two components, deliberately not one.** `.chip`/`.chip-ok`/`.chip-cancel`/`.chip-disabled` (common.css) is the row-verb affordance: fb-list.js's write (✓) / revert (✕) / exit (✕) on a dirty row, and a page's own approve/reject/view/delete/post/discard/retry icons. `.fb-tag` (common.css) is a labelled, bordered toggle or small action link ("+ Add reminder", "+ Upload document", "Save", "Cancel", "Open", "Delete" as text, not a glyph). **Shipped 2026-09-06** — both names had been `.chip` across different files, colliding, and the consequence wasn't just naming confusion: `.chip-ok`/`.chip-cancel` had **no colour rule anywhere in the codebase**, so every write/revert/approve/reject icon on every page using them (8+ FB.list pages, plus inbox.js's row verbs) rendered with no colour at all until this fix. New icon-only row verbs use `.chip` + `.chip-ok`/`.chip-cancel`/`.chip-disabled`; new labelled toggles/links use `.fb-tag`. Don't reuse `.chip` for a labelled link again — that's exactly how this happened.
- **Empty / loading / error states.** Consistent copy tone, consistent placement (centered in the content area the data would otherwise occupy), consistent use of `--text-muted`/`--text-faint`. Not ad-hoc inline strings styled per-screen. **Shipped 2026-09-07**, three parts:
  1. **Transient feedback has one channel, `FB.status`** (`fb-core.js`, "the ONE transient-feedback channel" — comment predates this fix). `bank-payments.js`/`bank-reconciliation.js` still had their own page-local `.msg-bank`/`#msg-payments`/`#msg-recon` spans (the exact "per-screen msg span" the comment says is retired) — migrated to call `FB.status.show`/`.clear()`, and the now-dead DOM nodes and CSS removed. If you're adding a save/load/error message to a screen that has the topbar (i.e. calls `navBar()`), it goes through `FB.status`, never a new local message element. `new-company.js`'s own `#msg` span is the one legitimate exception: that page renders no topbar at all (deliberately, K5 — no sidebar chrome), so `FB.status`'s target element doesn't exist there.
  2. **`.pe-ro` (read-only/muted text — a read-only field, an empty-state row, a load-failure row)** was `{ color:var(--text-muted); }`, defined identically in five separate files (accounting.js, calendar.js, documents.js, exchange-rates.js, settings.js). Moved to common.css; still to be applied via `class="pe-ro"`, unchanged.
  3. **Full-width table placeholder rows** ("Loading…", "No payments in range.", "Select an account.") repeated the same inline `style="text-align:center;color:var(--text-faint);padding:32px"` across 8 sites in bank.js/bank-payments.js/bank-reconciliation.js/payables.js. Now `class="table-empty"` on the `<td>` (common.css: `table td.table-empty`). The extra `table` in that selector isn't decorative — bank.js's/payables.js's own `.data-table td` rule is the same specificity as a bare `td.table-empty`, so without it the two fight it out by source order instead of by which one should actually win; this is exactly the kind of specificity collision the `.fb-locked-fields` note above already warns about.
- **Confirmation.** Destructive or hard-to-reverse actions (void, delete, post a period-locking entry) get an in-app confirmation component (`FB.modal`) that can show *what* is about to happen — not a bare `window.confirm()`. **Shipped 2026-09-06** — all 15 real `window.confirm()` call sites migrated. One thing to watch: `FB.modal`'s `title` is escaped internally, but its `body` is raw HTML (to allow legitimate formatting) — always `esc()` any interpolated value (a partner name, a filename) that lands in `body`, the same way you already would before concatenating it into any other HTML string.
- **Buttons.** One primary action per view. Four variants, all shipped and all driven by tokens: **primary** (`.btn-primary`, common.css — solid accent fill; the one forward action, e.g. Save/Post/Create), **secondary/neutral** (`.btn-sm` — outlined, `--bg` fill; Cancel/Back/Add Line and anything that isn't *the* action), **destructive** (`.btn-sm.danger` — the same shape as secondary but outlined in `--danger`, filling solid on hover; never a solid destructive button at rest, since `--danger` is deliberately lighter in dark mode for text-on-surface legibility and fails contrast as a hover-less solid fill), and **tertiary/inline** (`.fb-tag`, see the chip/tag bullet above — a labelled text action with no button chrome beyond a light border). Icon-only chrome (`.tb-icon-btn` in the topbar, `.tb-toggle-btn` for a segmented toggle) is a separate family for persistent navigation, not a view action, and isn't part of this ladder; same for the hover-reveal row affordance pattern (`.pay-afford`/`.void-afford`) and the `.chip`/`.chip-ok`/`.chip-cancel` row-verb icons documented above.

  **Shipped 2026-09-06** — `FB.modal` (this session's `window.confirm()` replacement) already renders its button row as exactly this three-class ladder (`b.primary ? 'btn-primary' : 'btn-sm'`, `+ (b.danger ? ' danger' : '')`), but chat.js's inline consent cards (Approve once / Always allow / Deny once / Never allow) — a different rendering path for the same *kind* of primary/neutral/destructive choice — had reinvented it from scratch as page-local `.chat-card button`/`.primary`/`.danger` classes with their own padding, radius, and hover recipe, rather than reusing the shared one FB.modal had just established. `#chat-perms button.revoke` (the permissions table's Reset action) and bill-edit.js's Void button (`.btn-sm` plus an inline `style="color:var(--danger);border-color:var(--danger)"` faking the danger modifier that already existed) had the same problem in miniature. All three now use the shared classes; the page-local recipes were deleted rather than kept as an "equivalent" shadow copy. `settings.js`'s `.action-btn` (a near-identical bespoke neutral-button recipe, differing from `.btn-sm` only in its denser table-row sizing) now extends `.btn-sm`'s colour/hover rule instead of repeating it, keeping only the sizing override page-local.

  **Shipped 2026-09-07**, a follow-up sweep of every remaining `<button>` in the codebase found two more: payables-bills.js's Draft toggle (the `~` add-bill-row button) carried `class="fb-toggle-btn"` — a name that was never defined anywhere, so it rendered as a bare native button with no on/off visual distinction beyond its own text ("Draft" → "Draft: ON"). It now reuses `.tb-toggle-btn`/`.tb-active` (common.css) — the same base+active pill recipe reports-hub's MoM/YoY toggle already uses for the identical two-state-toggle shape, despite the `tb-` name not being topbar-exclusive in practice. Separately, journal-voucher.js's read-only "attachments already on this posted entry" list (a different rendering path from the pending-attachment queue) duplicated `.fb-attach-row`/`.fb-att-del`'s exact recipe inline instead of using those two classes, which already existed in the same file for the pending-queue version of the same row.
- **Posted vs. draft.** The single most domain-specific requirement: an immutable/posted document must be visually distinguishable from an editable draft, consistently, on every screen that shows either state — this is an auditability requirement, not a styling preference. **Shipped 2026-09-06**, two parts:
  1. `.fb-locked-fields` (common.css) — toggle this class on a field container once a record becomes non-draft/locked; it flattens inputs/selects/textareas to plain, borderless, muted-color text. Used by journal-voucher.js and bill-edit.js's header fields; line-item grids that individually `.disable` each input (bill-edit.js's `.bl-cell`) get the same look via native `:disabled` instead, which is fine — the visual outcome is what has to match, not the mechanism. If you're adding this to a page whose fields already have their own `:disabled`/`[readonly]` background override (there was exactly one such collision, in journal-voucher.js, from an unrelated disabled-state rule predating this component), add a same-shape compound override *in that page's own stylesheet* rather than fighting it from common.css — see journal-voucher.js's comment at the `.fb-locked-fields` block for the worked example.
  2. A 🔒 prefix on the status badge text itself for every status that represents a locked/immutable state (posted, void, reversed, paid, partial, overdue — everything except an editable draft/proposed/new). This is a second, non-color-dependent signal, not decoration: colour alone silently excludes colourblind users from "is this locked" being scannable at a glance. Implemented in journal-voucher.js's `updateStatusBadge()` and bill-edit.js/payables-bills.js's `statusBadge()`.

  Not yet touched: any other editable-then-postable record type introduced later should reuse both parts rather than inventing a per-page equivalent — that's exactly how this became five inconsistent conventions the first time.

## Accessibility

- **Contrast:** WCAG AA — 4.5:1 for body text, 3:1 for large text (≥1.5rem or ≥1.125rem bold). This applies to token *and* hardcoded colours alike — a token doesn't get a pass just for being a variable. `--text-faint` is exempted only because it's restricted to decorative, non-text use (see Colour & Theming).
- **Focus:** interactive elements must have a visible `:focus-visible` state using `--focus-ring` — not `:focus` alone (which also fires on mouse click) and never `outline: none`/`outline: 0` without a replacement ring. Keyboard navigation is a primary input mode for fast data entry here, not an edge case.
- **Hover:** interactive elements also get a `:hover` state, but hover is a supplement to focus, not a substitute for it.
- **Disabled / placeholder elements** use `opacity: .4` or `cursor: not-allowed` — do not remove them from the DOM.
- **Icon-only buttons** get an `aria-label` (a `title` attribute may be added additionally for a mouse-hover tooltip, but `aria-label` is the accessible name and is required — `title` alone is not a reliable substitute for screen readers).
- **A `title` tooltip never repeats a keyboard shortcut.** It states the action in plain words only — `title="Approve"`, not `title="Approve (y)"` — the same way its paired `aria-label` already does. Shortcut hints live exclusively in the `?` shortcut-help screen; a tooltip that also carries one is teaching the same fact twice in two different places that can drift out of sync with each other (and with the real binding) the next time either is edited separately. **Shipped 2026-09-09** (Inbox rebuild) — every row-verb tooltip on that page (`approve (y)`, `reject (x)`, `discard (x)`, etc.) had the shortcut baked in; swept to plain-word text. **App-wide sweep, same day**: the same pattern existed outside Inbox — highest-leverage fix was `fb-list.js` itself (`fold (Space)`, `write (w)`, `exit (Esc)`, `revert (u)` — shared by every FB.list page at once), plus one instance each in `fb-attachments.js`, `bill-edit.js`, `journal-voucher.js`, `calendar.js`, and two in `payables-bills.js`. A newly-documented principle only protects the page it was written for until it's actually checked against the rest of the app — grep for `title="[^"]*(<letter>)"` periodically rather than assuming a session's fix was exhaustive. **Second follow-up, 2026-09-10**: the app-wide sweep's own regex only matched single letters, so it missed a leader-key sequence (`title="Switch company (g w)"`, a space between the two keys) and a bare symbol (`#tb-help-btn`'s `title="Keyboard shortcuts (?)"` — the button that opens the shortcut-help screen was reminding you of its own shortcut). A grep for this pattern needs to match spaces and symbols inside the parens too, not just `[A-Za-z]`, or it will keep re-finding "everything's clean" falsely.
